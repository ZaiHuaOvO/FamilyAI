# V1.1：流式输出、对话历史与请求日志

> 状态：**已完成（2026-10-18）**  
> 前置：V1（`v1.0.0`）已完成  
> 产出：SSE 流式聊天、客户端携带的对话历史、请求日志查询接口与查看页面

## 1. 目标

在保持 V1 安全边界不变的前提下改善调用体验：

- 聊天支持逐字输出，降低长回答的等待感。
- 客户端可以把历史对话传给服务端，获得多轮上下文。
- 提供一个查看请求元数据的页面，便于排查问题。
- 服务端仍然不持久化聊天内容，日志中仍然不出现聊天正文或 Token。

## 2. 设计决定

| 需求 | 方案 | 原因 |
|---|---|---|
| 流式输出 | 新增 `POST /api/v1/chat/stream` | 保持现有 `/chat` 契约不变，客户端可按需选择 |
| 对话历史 | 在请求体中增加可选 `history` | 服务端不持久化；由客户端控制上下文 |
| 请求日志 | 内存环形缓冲 + `GET /api/v1/logs` | 只记录元数据，进程重启即清空 |
| 日志页面 | `GET /api/v1/logs/view` 渲染 HTML | 页面本身不含数据，数据接口仍要求 Token |

### 2.1 流式协议

响应类型：`text/event-stream`。

```text
event: delta
data: {"delta": "家庭"}

event: delta
data: {"delta": "自建"}

event: done
data: {"model": "qwen3.5:4b", "duration_ms": 3449}
```

上游错误（模型不可用、超时等）在流开始后以事件返回：

```text
event: error
data: {"detail": "model service unavailable", "status": 503}
```

规则：

- 认证、请求格式、消息/历史校验、频率限制失败仍返回普通 HTTP 错误（401/422/429）。
- 流一旦开始（HTTP 200 与响应头已发送），上游错误和并发已满以 `event: error` 返回。
- 并发槽位在生成器内部获取，客户端在响应开始前断开不会泄漏槽位。
- 客户端断开时生成器被取消，`finally` 释放槽位。

### 2.2 对话历史

```json
{
  "message": "我最喜欢的颜色是什么？",
  "history": [
    {"role": "user", "content": "请记住：我最喜欢的颜色是蓝色。"},
    {"role": "assistant", "content": "好的，我记住了：蓝色。"}
  ]
}
```

约束：

- `role` 只能是 `user` 或 `assistant`，不接受 `system`。
- 历史消息最多 `MAX_HISTORY_MESSAGES`（默认 20）条。
- 历史内容总字符数最多 `MAX_HISTORY_CHARS`（默认 12000）。
- 每条历史内容去空白后必须非空。
- 当前 `message` 仍受 `MAX_MESSAGE_CHARS` 限制。
- 服务端不做持久化；客户端下一次请求需要重新携带历史。

### 2.3 请求日志

- 内存环形缓冲，默认最多 200 条，进程重启清空。
- 只记录：时间（UTC）、方法、路径、状态码、耗时、来源 IP。
- 不记录：Token、请求头、查询参数、聊天正文、模型回答。
- `GET /api/v1/logs?limit=50` 需要 Token，返回最新记录。
- `GET /api/v1/logs/view` 是无需认证的 HTML 页面；页面要求输入 Token 后从 `/api/v1/logs` 拉取数据，Token 只保存在页面内存中。

## 6. 已知限制

- 访问日志中间件对 `/chat/stream` 记录的耗时是“返回响应头”的时间（数毫秒），真实生成耗时在 `done` 事件中。
- 请求日志只保存在内存中，进程重启后清空；多进程部署时不共享。
- 流式客户端必须处理 `event: error`。
- 历史完全由客户端提供，服务端不做校验之外的处理，也不持久化。
