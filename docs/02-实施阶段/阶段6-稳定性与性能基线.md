## 1. MacBook 作为服务器的现实限制

M3 + 16GB 足以运行较小模型并服务家庭低并发请求，但 MacBook 是笔记本：

- 合盖、睡眠、断网、系统更新或重启都可能中断服务。
- 锁屏、显示器关闭是否影响服务，需要实测确认，不能假定。
- 长时间测试时保持连接电源。
- 不要在第一天同时引入 launchd、Docker、反向代理、自动更新和公网访问。

V1 面向自己与家人少量使用，不以高并发、多人同时推理或云服务级可用性为目标。

## 2. 运行方式

### 2.1 手动运行（V1 默认）

```bash
uv run uvicorn family_ai_api.main:app --host 0.0.0.0 --port 8000
```

- 长期运行时不要使用 `--reload`。
- 先确认服务稳定，再考虑登录自启动。
- 可把启动命令记录到本文档，但不要写入真实 Token。

### 2.2 后续可选：登录自启动

稳定运行一段时间后再评估 launchd。引入前需要确认：

- 工作目录、虚拟环境与 `.env` 路径正确；
- 日志位置与轮转；
- 失败重启策略；
- 如何停止与卸载服务。

V1 不要求完成这一项。

### 3.5 本机稳定性实测（2026-10-18）

- 连续 20 条请求全部成功，服务未崩溃。
- 两条并发请求均成功；第三条同时到达时返回 429，符合并发上限设计。
- 并发时 Ollama 模型占用从约 4.1GB 升到 7.1GB，swap 使用约 6.0GB，系统空闲内存约 24%。
- 结论：16GB 机器上并发 2 可用，但内存压力明显。如果系统出现卡顿，优先把 `MAX_CONCURRENT_REQUESTS` 调为 `1`。
- Ollama 进程被停止后，macOS 应用会自动重启服务；模型会在空闲后卸载，内存随之释放。

## 4. 稳定性测试要求

- 连续 20 条常规请求不崩溃、不出现无限等待。
- Ollama 停止时，FastAPI 在超时时间内返回明确错误（503/504）。
- 重启 FastAPI 后服务恢复；重启 Ollama 后聊天恢复。
- 出错时能在日志中找到原因，但日志不含 Token 和聊天正文。

## 5. 性能不达标时

按以下顺序调整，不要先加复杂基础设施：

1. 降低模型体量（更小的量化或参数）。
2. 降低上下文长度 / 输入长度上限。
3. 降低并发上限（`MAX_CONCURRENT_REQUESTS=1`）。
4. 关闭其他占内存的应用。
5. 重新测量，记录调整前后的差异。
